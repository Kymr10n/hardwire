# Decisions

Append-only log. Every change to `docs/SPEC.md` gets an entry here in the same commit (enforced by `tools/check.sh`).
Format: `## D-NNN — YYYY-MM-DD — Title`, then **Decision**, **Why**, **Affects** (spec sections, balance keys, tests). Never edit or delete old entries; supersede them with a new one.

## D-001 — 2026-10-19 — Engine: Godot 4, GDScript

**Decision:** Godot 4 with GDScript and the Compatibility renderer.
**Why:** Open source, strong 2D, exports to every target, simple language that AI tools write well.
**Affects:** Overview, Technical architecture.

## D-002 — 2026-10-19 — Name: Hardwire

**Decision:** The game is called Hardwire (working title was Overclock).
**Why:** Short, fits the hardware theme; no well-known mobile game with that name found. Confirm when reserving store listings.
**Affects:** Overview.

## D-003 — 2026-10-19 — Per-stat gating, separate currency, generated tiers, no failure penalty

**Decision:** Slots check each stat separately; upgrades cost Cycles, not stats; tiers are generated by formula; failure gives a fresh sequence with no penalty.
**Why:** Forces variety across minigames, keeps stats monotonic, makes the game endless, keeps it fair.
**Affects:** Stats, currency and slot gating; Difficulty curve; Core loop.

## D-004 — 2026-10-19 — Idle income: Cycles only, capped at 8 h

**Decision:** Earn Cycles while away at about 6 replays per hour of the highest solved tier, capped at 8 hours; never stats.
**Why:** Rewards returning without replacing the puzzles as the way to progress.
**Affects:** Idle income; `balance.json` → `idle`.

## D-005 — 2026-10-19 — Benchmark slot after the prototype

**Decision:** Every 5th tier gets a chained three-minigame Benchmark slot, built after M8. Puzzle code must stay chainable now.
**Why:** Variety and a milestone moment without growing the prototype.
**Affects:** After the prototype; PuzzleBase design.

## D-006 — 2026-10-19 — No monetization

**Decision:** Free; no ads, purchases or tracking SDKs.
**Why:** Hobby project; keeps code and store privacy forms minimal.
**Affects:** Whole project.

## D-007 — 2026-10-19 — Targets: phones, PC and Steam Deck

**Decision:** Targets are Android, iOS, Windows, Linux, macOS and Steam Deck (native Linux build). Phones are portrait; PC and Deck are landscape. All input goes through InputMap actions and works with touch, mouse, keyboard and gamepad. Web is not a target. Supersedes the earlier "Android and web first, portrait only, touch only" plan.
**Why:** The owner wants the game on phones, PC and Steam Deck. Steam Deck Verified requires full controller support, matching glyphs and legible text at 1280 × 800.
**Affects:** Overview; new section Platforms and input; Screens; Technical architecture; Milestones M1–M5, M8.

## D-008 — 2026-10-19 — iOS and macOS builds need a recent Mac

**Decision:** Develop and test on Linux, Android and Steam Deck first. iOS and macOS release builds wait until a Mac with current Xcode or a cloud macOS build service is available.
**Why:** Since 28 April 2026 App Store uploads require Xcode 26, which needs a recent macOS; the owner's 2016 MacBook Pro can't run it. macOS signing and notarization also need a Mac.
**Affects:** Platforms and input.

## D-009 — 2026-10-19 — Development harness

**Decision:** Claude Code works under `CLAUDE.md`, hooks in `.claude/`, and the single quality gate `tools/check.sh` (format, lint, drift checks, script errors, GUT tests), also run in CI. Tool versions are pinned in `tools/versions.env`.
**Why:** Keep the code small and consistent with the spec across many AI sessions; catch drift automatically instead of by memory.
**Affects:** Technical architecture; all milestones.

## D-010 — 2026-10-19 — Replay counts follow the formulas

**Decision:** The spec says about 8 replays per minigame in total to reach tier 10 and about 24 to reach tier 20 (not 6 at tier 9 and 15 at tier 19).
**Why:** A simulation of `req(T)` and `reward(T)` with first-solve doubling gives these numbers; the formulas stay, the text was wrong.
**Affects:** Difficulty curve.

## D-011 — 2026-10-19 — Storage Decoy placement; M2 covers Storage modifiers

**Decision:** The Decoy flashes dimly with a quieter tone, between two real items, on a pad different from both neighbors. Reverse and Decoy are part of M2 (testable when forced).
**Why:** The spec left the decoy's position open; forced modifiers keep the three minigames consistent.
**Affects:** Minigame: Storage; Milestones (M2).

## D-012 — 2026-10-19 — RAM counter, Commit and time limit use cells needed

**Decision:** Cells needed is `filled`, or `n² − filled` with Inverted; the counter, the Commit gate and the input time (4 s + 0.8 s per cell needed) use it. Rotated shows a clockwise arrow for the whole attempt.
**Why:** Read literally, Inverted would unlock Commit at the wrong count and give time for the wrong number of cells.
**Affects:** Minigame: RAM; Difficulty curve (RAM formula).

## D-013 — 2026-10-19 — CPU input end rule, failure reveal, Syncopated

**Decision:** Input ends 600 ms after the release of the last beat, or once no input could still pass (every segment at its upper tolerance, plus 600 ms); a press beyond `beats` fails at once. On failure the tile replays the rhythm silently, compressed into 1 s. Syncopated allows 0.5 and 1.5 steps and always contains one.
**Why:** "600 ms after the last expected release" would cut off a uniformly slow but in-tolerance player.
**Affects:** Minigame: CPU; `balance.json` → `cpu.syncopated_steps`.

## D-014 — 2026-10-19 — Reward rounding, slot hash, overview order, debug panel

**Decision:** All reward factors multiply and the result is rounded. The slot hash is FNV-1a (32 bit) of `"<tier>:<type>"` (low 16 bits roll the chance, high 16 bits pick the modifier). Tier 1 is at the top of the overview; cards are RAM, CPU, STO. The debug panel opens with 5 taps on the stat bar within 3 s; its time scale never affects rhythm judging.
**Why:** The spec left rounding, the hash and the order open; a platform-stable hash keeps slots identical everywhere.
**Affects:** Difficulty curve; Screens and UX flow; Technical architecture; `balance.json` → `debug`.

## D-015 — 2026-10-19 — Upgrade cost rounding, Replay buffer, Time dilation on CPU

**Decision:** Cost = `round(base × growth^level)`. Replay replays the sequence, resets progress and restarts the timer. Time dilation multiplies the Storage and RAM time limits and the CPU first-press timeout. Assist levels reach puzzles through `SlotDef.assist`.
**Why:** The spec did not define these cases; puzzles must still not read GameState.
**Affects:** Upgrade shop.

## D-016 — 2026-10-19 — Idle amount and dialog timing; Rebuild keeps seen hints

**Decision:** Idle Cycles = `round(rate × min(hours, 8) × (1 + 0.10 × Cycle miner) × (1 + 0.25 × Cores))`, offered on the overview only (never over a running puzzle). Rebuild keeps the first-run hints already seen.
**Why:** Precise numbers for tests; a dialog over a running puzzle would cost the attempt.
**Affects:** Idle income; Prestige.

## D-017 — 2026-10-19 — First-run hints, transitions, back button

**Decision:** The first attempt starts when the player dismisses the one-line hint; screens fade in over 150 ms; back returns to the overview and quits only from the overview or boot screen on phones.
**Why:** Concrete behaviour for M8 polish.
**Affects:** Screens and UX flow.

## D-018 — 2026-10-19 — Open source under MIT; Licenses screen

**Decision:** Hardwire is MIT-licensed. Settings → Licenses shows the full texts of Hardwire, the JetBrains Mono font (OFL) and Godot with its third-party components.
**Why:** Publishing on GitHub; distributed builds must carry the engine's and the font's license texts.
**Affects:** Screens and UX flow; export presets (include `LICENSE`, the OFL text).

## D-019 — 2026-10-19 — Steam Deck and desktop (M9)

**Decision:** Landscape layouts chosen by window aspect (base 1920 × 1080, one code path per screen), full gamepad and keyboard control through InputMap actions, a Linux build that starts fullscreen when `SteamDeck=1`, and Fullscreen and Quit in Settings on PC.
**Why:** The owner plays on a Steam Deck; a later Steam release needs Deck Verified behaviour.
**Affects:** Overview (Decisions table); Screens and UX flow; Milestones (M9).

## D-020 — 2026-10-19 — Development harness adapted to this codebase

**Decision:** The harness from D-009 is adopted with these adaptations: GUT stays vendored in `addons/gut` (the pin in `tools/versions.env` is checked, not installed); the single portrait/landscape switch is `Main` plus `Ui.is_landscape()` rather than a Layout autoload; milestone status lives only in `docs/PROGRESS.md`; test files with more than 12 cases opt out of gdlint's `max-public-methods` with a `# gdlint: disable` line; the drift check compares allowed numbers by value and treats multi-line constants as constants.

## D-021 — 2026-10-19 — Platforms and controls reconciled with what was built

**Decision:** Supersedes parts of D-007. Web stays as an extra target next to Android, iOS, Windows, Linux / Steam Deck and macOS. Storage keeps aim-and-press on gamepad and keyboard (focus a pad, confirm) in the same ring as on touch, instead of direct pad buttons and a diamond layout. RAM commit is Y / C, because Enter is Confirm. Prompts show glyphs for the last-used device (a small InputMode autoload), the minimum font is 32 px at the reference size, Boot says "Press any button", the debug panel also opens with F1 or gamepad View, and Backspace also goes back.
**Why:** Aim-and-press works for every pad count with one layout and is already built and tested; Web costs nothing to keep; glyphs and legible text are Deck Verified requirements.
**Affects:** Overview; Platforms and input; Minigame: Storage; Screens and UX flow; `project.godot` input map; theme font sizes.

## D-022 — 2026-10-19 — CPU judges beats and holds, not tap length; beat markers show lengths

**Decision:** The rhythm judge checks the time from each press to the next (every beat lands in rhythm) and the hold time of holds (on-segments longer than one step). Taps (one step or shorter) pass however briefly they are pressed, and gaps are not judged on their own. Under the tile, one marker per beat shows its length: a dot for a tap, a bar as long as its steps for a hold; under Audio only every marker is a plain dot that fills only for presses. The input window still ends at the longest passing rhythm, which caps how long the last beat (even a tap) may be held. Supersedes the segment-by-segment judging and the end-rule wording of D-013. The existing one-line modifier hints ("Listen", "Half steps", "Set the dark cells", "Enter it rotated") are now specified.
**Why:** Play-testing with a mouse: a natural click lasts 100–150 ms, but a 1-step tap at tier 1 had to be held 210–390 ms, so perfectly timed taps failed. Holds were hard to read during playback. Under Audio only, length markers would show the rhythm the modifier hides.
**Affects:** Minigame: CPU (Watch phase, Input phase, Judging); `RhythmJudge`, `CpuPuzzle`; tests `test_rhythm_judge`, `test_cpu_puzzle`.

## D-023 — 2026-10-19 — Spec reconciled with the reviewed implementation

**Decision:** The spec now states what the code already does and the review found unspecified: unlocked slot cards show what the next solve pays; the result overlay notes "First solve ×2"; the stat bar shows 12.3K / 4.56M above 9999; requirement chips are accent-coloured while unmet; the game also saves on window close and app pause; gamepad focus opens on the first unsolved slot of the newest unlocked tier; an orientation flip re-creates the screen and restarts a running attempt with a fresh sequence; the license text scrolls with the D-pad or arrows. Modifier names are shown as Reverse, Decoy, Inverted, Rotated, Audio only, Syncopated (one table in `SlotDef`). Back from Licenses returns to Settings for the button and for B / Esc alike. The CPU input window runs in real time at every debug time scale, like the judging. The game caps at 60 fps (`application/run/max_fps`). Wording fixes: two game actions (`commit`, `debug_panel`); M1's "Done when" says window, not portrait window; the folder structure lists the current files. All colours, sizes and durations used by UI code live in the theme (new constants: `hint_dim_pct`, `dialog_dim_pct`, `overlay_dim_pct`, `dialog_width`, `button_width`, `tier_label_width`, `trace_width`, `row_gap`) and all audio tuning in `balance.json` (`audio.buffer_s`, `audio.fail_volume`); the drift check now scans every scene and autoload for stray numbers.
**Why:** A whole-project audit found the implementation ahead of the spec text in these places; recording them keeps the spec the source of truth. The time-scale rule made the CPU minigame unplayable above 1× in the debug panel.
**Affects:** Platforms and input; Difficulty curve > Modifiers; Screens and UX flow; Save system; Technical architecture; Milestones (M1); theme; `balance.json` → `audio`; `tools/drift_check.py`.

## D-024 — 2026-10-19 — Rumble with the rhythm, while holding, and on results

**Decision:** In the CPU minigame the controller rumbles during playback for each on-segment, as long as the tile is lit (phones: one vibration per beat), and during input for as long as the tile is held; this replaces the single pulse per press. Under Audio only, playback does not rumble (only the tone plays). In every minigame a success gives a short double pulse and a failure one long pulse. Everything goes through the Haptics autoload and the haptics setting; the lengths and strengths live in `balance.json` → `haptics`.
**Why:** Owner request after play-testing with a controller: feeling the rhythm makes holds readable and the Deck's rumble is otherwise unused. Audio only must stay an ear-only test.
**Affects:** Platforms and input > Haptics; Minigame: CPU; Result overlay; `balance.json` → `haptics`; `Haptics`, `CpuPuzzle`, `PuzzleBase`.

## D-027 — 2026-10-19 — Add a restrained procedural ambient score

**Decision:** The game plays a quiet, seeded ambient score through `AudioStreamGenerator`: a slow
four-bar minor-pentatonic progression, smooth low sine bass, faint octave harmonics, and sparse
upper notes. Music and sound effects share the Sound setting; every musical tuning value lives in
`balance.json` → `audio`.
**Why:** The owner requested minimal electronic music that gently supports play, varies between
sessions, and avoids an intrusive repeating melody or percussion.
**Affects:** Visual and audio style; `MusicGen`; `Synth`; `balance.json` → `audio`.

## D-028 — 2026-10-19 — Pause ambient music outside gameplay screens

**Decision:** The ambient score runs on Overview and Puzzle screens, and pauses on Boot, Shop,
Settings, Licenses and the debug menu. Pausing stops score voices but lets gameplay sound effects
finish.
**Why:** Keeping the minimal score within active gameplay avoids filling the boot and utility menus
with background sound.
**Affects:** Screens and UX flow; `Main`; `Synth`; ambient music tests.

## D-029 — 2026-10-19 — Ambient score gets a soft beat and high notes

**Decision:** Supersedes the "no percussion" part of D-027. The score adds a soft half-time beat (a
pitch-dropping sine kick on beats 1 and 3 with the bass, a short noise hi-hat on every off-beat)
and two or three short high notes per bar, three octaves above the bar's root, on seeded
eighth-note positions. Upper and high notes use the minor pentatonic of the current bar's root, so
the scale moves with the bass. The spec names the screens where the score pauses (D-028). All
tuning stays in `balance.json` → `audio`.
**Why:** The owner listened to the score in game and asked for high notes on top and a fitting beat.
**Affects:** Visual and audio style; `MusicGen`; `Synth`; `balance.json` → `audio`.

## D-030 — 2026-10-19 — CPU judged as you play; wider tolerance

**Decision:** The CPU minigame judges each check the moment the input determines it: a beat's interval when the next press lands, a hold when it is released. The first check out of tolerance ends the attempt at once: that beat's marker turns red and the hint line above the tile says why ("Beat 3 too late", "too early", "held too short", "held too long"). The attempt succeeds at the release of the last beat. The 600 ms grace after the last release and the "press beyond `beats` fails" rule are gone (input has already ended); the longest-passing-rhythm cap stays as a stall guard. Tolerance is `max(0.25, 0.40 − 0.0075(T−1))` with a 100 ms minimum (was 0.30 to 0.15, 60 ms). Supersedes the input-end rule of D-022 and D-013 and the tolerance formula.
**Why:** Play-test: the game was not fun. The player pressed blind and learned pass/fail 600 ms after the last release without knowing which beat was wrong, and the timing felt too strict. Failing at the first miss with the reason shown is how Storage already behaves on a wrong pad.
**Affects:** Minigame: CPU (Input phase, Judging); Difficulty curve (formulas, sample tiers); `balance.json` → `cpu` (`tolerance_start`, `tolerance_min`, `tolerance_abs_ms`; `end_grace_ms` removed); `RhythmJudge`, `CpuPuzzle`, `CpuMarkers`; tests `test_rhythm_judge`, `test_rhythm_gen`, `test_cpu_puzzle`.

## D-034 — 2026-10-19 — Rumble for every button and all playback

**Decision:** Every button press (menus, slot cards, dialogs, Again / Overview, the Settings toggles, Replay, Commit, the debug panel), the boot tap and the hint tap give the light haptic pulse. One home: the Haptics autoload connects the `pressed` signal of every `BaseButton` that enters the tree, so screens never call it for buttons. During a Watch phase the controller rumbles for as long as playback lights something: each Storage pad while it is lit (decoys at `haptics.decoy_strength`), the RAM pattern while it shows, and the CPU tile for each on-segment as before (Audio only stays silent). Phones get one vibration per lit thing or press. Extends D-024.
**Why:** Play-test on the Steam Deck: the owner wants full immersion; menus and the Storage and RAM playback were silent while the CPU game rumbled.
**Affects:** Platforms and input > Haptics; Minigame: Storage and RAM (Watch phase); Screens and UX flow (Feedback on every input); `balance.json` → `haptics.decoy_strength`; `Haptics`, `StoragePuzzle`, `RamPuzzle`, `ShopScreen`, `BootScreen`, `HintOverlay`; `test_haptics`, `test_balance`.

## D-036 — 2026-10-19 — Louder bass; the beat builds over the first phrases

**Decision:** Supersedes "the beat is fixed" in D-029. The bass is louder (volume 0.36, octave
harmonic 0.07). The beat builds over the first three four-bar phrases of a session and then stays:
kick on 1 and 3 with off-beat hats; from bar 5 a soft noise snare on 2 and 4; from bar 9 quiet
ghost hats on the sixteenth before each beat. The last bar of every phrase adds a pickup kick on the "and" of 4.
Still 72 BPM half-time, no new instruments beyond noise and the sine kick.
**Why:** The owner wanted the bassline a bit louder and the beat more progressive but still chill.
**Affects:** Visual and audio style (Audio); `MusicGen`; `Synth`; `balance.json` → `audio`.

## D-037 — 2026-10-19 — Storage pads light, sound and rumble while held

**Decision:** During Storage input a pressed pad stays lit, sounds its tone and rumbles for as long
as it is held, with at least 180 ms of light (`tap_flash_ms`) and the minimum note length
(`pad_note_min_ms`) so a quick tap still shows. The press still counts as the tap: a wrong press
fails at once without lighting or sounding the pad (the correct pad is revealed), and the last
correct press solves and still shows its minimum light. A release ends the hold even if focus moved
while holding; a second press moves the hold to the new pad. A puzzle freed mid-attempt (screen
rebuilt on rotation or resize) aborts, so no tone or rumble outlives it.
**Why:** Play-test: the owner wants intuitive feedback while repeating the pattern; it matches
the CPU tile (tone and rumble while held) and Watch playback (rumble while a pad is lit).
**Affects:** Minigame: Storage (Input phase); Platforms and input (Haptics); `StoragePad`,
`StoragePuzzle`, `PuzzleBase` (abort on exit), `Synth.start_note`; tests `test_storage_puzzle`,
`test_polish`.

## D-038 — 2026-10-19 — One-click Steam Deck install and tagged releases

**Decision:** Players install on a Steam Deck the EmuDeck way: download `Hardwire-SteamDeck.desktop` from the latest GitHub release, double-click it in Desktop Mode, done. It runs `tools/steamdeck_install.sh`, which fetches the latest release's Linux build into `~/Games/hardwire`, registers it as a non-Steam game with `tools/steamdeck_shortcut.py` (Steam is closed and restarted around the edit of `shortcuts.vdf`), carries a 0.1.0 save into the `Hardwire` save folder, and updates the game when run again. Releases are made by pushing a tag `v<version>`: `.github/workflows/release.yml` checks the tag against `config/version`, exports Linux, Windows and Web and publishes them with the installer and the CHANGELOG section as notes. `tools/deck.sh` stays the developer's SSH path.
**Why:** The owner wants an idiot-proof install for the Deck without SSH or Steam's add-a-game dialog; EmuDeck's download-and-double-click flow is what Deck users know. An install that follows the latest release needs releases to be one command.
**Affects:** Technical architecture (folder structure); `tools/steamdeck_install.sh`, `tools/steamdeck_shortcut.py`, `tools/Hardwire-SteamDeck.desktop`, `docs/icon.png`, `.github/workflows/release.yml`; README (Steam Deck), CONTRIBUTING (releases).

## D-039 — 2026-10-21 — Cold Boot visual redesign (M11)

**Decision:** The look changes from the rounded "flat circuit board" to **Cold Boot**: a flat industrial diagnostic terminal drawn with the same Godot shapes and font. Square corners everywhere, near-black green-grey surfaces with 2 px outlines, phosphor green as the one UI accent (focus, pressed, "Your turn", success, `SYSTEM READY`), amber only for attention (unmet requirement chips, `REBUILD AVAILABLE`, the enabled Rebuild button and its confirm button), red only for failure. The stat hues are retuned so amber is free for attention: RAM cyan, CPU violet, STO orange; they mark module identity only (stat values, card and header titles, timer fill, lit cells and tile). The Storage pad palette stays. CPU beat markers are square ticks and bars instead of dots (amends the wording of D-022; the semantics stay). The Boot screen shows a short check list from real state (save state, Cores, best tier, then `SYSTEM READY`) that any press skips; the overview gets a one-line system header with a truthful status. Section, phase and status labels are drawn uppercase; body text stays normal case. The design language (tokens, semantics, geometry, motion, vocabulary) lives in `docs/DESIGN.md`; every value lives in the theme. Gameplay, balance, saves, input and architecture do not change. Added as milestone M11.
**Why:** The owner wants the game to feel like a real computer being booted, diagnosed and rebuilt: cold, precise and credible, not a generic dark dashboard. The old amber STO colour collided with the warning colour the look needs; the owner chose to retune the stat hues rather than drop the warning colour.
**Affects:** Overview (Art row); Visual and audio style (Visuals); Screens and UX flow (Boot and Overview rows, Slot card states); Minigame: CPU (Watch phase markers); Milestones (M11); `docs/DESIGN.md` (new); `theme/hardwire_theme.tres`; `scenes/ui/*`, `scenes/screens/*`, `scenes/puzzles/StoragePad`, `RamGrid`, `CpuTile`, `CpuMarkers`; tests `test_polish`, `test_overview`, `test_input_mode`.

## D-040 — 2026-10-21 — The 12-method limit excludes static helper namespaces

**Decision:** The "≤ 12 public methods per class" rule in `CLAUDE.md` applies to classes with state. A file of pure static builders (`scenes/ui/Ui.gd`, 17 helpers after M11) is exempt, which matches what gdlint's `max-public-methods` already enforces. `gdlintrc` is unchanged.
**Why:** The limit exists to keep stateful classes small; a static helper namespace grows with the number of shared UI patterns, and splitting it by rule alone would scatter related helpers without making anything simpler. The mismatch surfaced in the M11 review.
**Affects:** `CLAUDE.md` (Principles > Small units). No spec change.

## D-041 — 2026-10-21 — Cold Boot, powered on (M12)

**Decision:** The Cold Boot look (D-039) gets the atmosphere of a powered-on terminal, at a noticeable but legible intensity. (1) The palette takes a phosphor tint: text and dim text are pale and grey green instead of grey, surfaces have a faint green cast. (2) One full-screen glass overlay shader on its own canvas layer draws a radial vignette (always), horizontal scanlines, a slight bloom of bright pixels and a slow 2 % brightness flicker (about 1.3 Hz, far below any flash risk); a Settings toggle "CRT glass" turns scanlines, bloom and flicker off and persists as `settings.crt` (default on). This supersedes the "no shaders" clause of D-039 for this one overlay; all its values are theme constants. (3) The Boot screen types its check list character by character with a block cursor and a soft tick, with memory checks from real state ("MEMORY CHECK ..... RAM 140 OK"), a power-on tone and the title fading in; any press still starts at once. (4) A machine sound bed: a faint filtered-noise hum under the overview and puzzles (with the score), a key click on every button, a relay click on every puzzle phase change. (5) Terminal texture: dialog titles become an inverted header strip, the overview status ends in a blinking cursor; the stat bar becomes a readout with a lamp per value that flashes and counts up on change; tags gain a little vertical padding; tier nodes light up (outline locked, filled unlocked, accent when the tier is fully solved) with traces between the cards; the puzzle sits in a bezel with corner ticks that pulses accent on success and red on failure, the timer is a segmented bar, and a status square blinks during input. Gameplay, balance formulas, input and the save schema (bar the new boolean) are unchanged. Added as milestone M12.
**Why:** Play-testing M11 fullscreen: the owner found the look too bland and not immersive, grey on black with nothing alive behind the glass. The owner chose all four packages and the "noticeable" intensity.

## D-042 — 2026-10-22 — Renderer: Mobile (Vulkan), Compatibility on the web only

**Decision:** The project renders with Godot's Mobile method, which runs on Vulkan on Linux, Windows, Android and the Steam Deck and on Metal on macOS and iOS. The Web export keeps the Compatibility renderer through the `renderer/rendering_method.web` override, since browsers support nothing else. Mobile rather than Forward+ because the game is 2D UI and Mobile is the lighter of the two Vulkan renderers. The Windows build stays on Vulkan; Direct3D 12 is not enabled. Supersedes the renderer clause of D-001; the game code is renderer-agnostic (the glass overlay is a plain `canvas_item` shader), so nothing else changes.
**Why:** The owner wants the game to render directly through Vulkan on desktop and the Deck instead of OpenGL. Known trade-offs, accepted: the web build looks slightly different from native, and a few very old Android devices without Vulkan drop out.
**Affects:** Overview (Engine row); Technical architecture (Project settings → Renderer); `project.godot` (`config/features`, `[rendering]`).
